SQL · Late returns

Which categories earn. Which copies never come back.

Clerk call list. Manager scorecard. Nightly refresh. Public rental sample.

A rental chain does not only need a sales total. A title that looks in stock is still unavailable if the disc is sitting in someone’s house.

SQL case on a public sample database (Sakila-style DVD rental / WGU Advanced Data Management). Course work, rewritten as an operations report — not a live client.

2Layers: clerk call list + store-category scorecard
NightlyStored procedure refresh after close

Problem

Revenue can look healthy while copies sit in living rooms. Staff need a call list. Managers need store × category, not 16,000 rental rows.

Approach

Functions recode active flags and classify On Time / Late / Still Out. A trigger rolls each insert into the summary. A procedure reloads both tables after close.

Insight

High revenue plus a high late-return rate is a warning: demand is there, inventory is not recirculating. Inactive accounts that still have a disc are first on the list.

Impact

Morning shift gets a current Still Out queue without querying live rental tables all day. District can compare the same category across stores.

The question

Built on the public DVD rental sample database (the same Sakila-style schema used in WGU’s Advanced Data Management course). The operating question is practical:

Which stores and film categories are earning rental revenue, and which of those same categories are tying up copies because customers bring them back late or not at all?

District managers need to know whether a high revenue number is healthy, or whether it is being propped up by titles that do not recirculate. Store staff need a list they can actually call.

What shipped

A PostgreSQL reporting layer, not a one-off query:

  • Detailed table — one row per rental: customer, store, title, category, payment, account status, return status.
  • Summary table — one row per store and category: volume, revenue, on-time / late / still-out counts, and late-return percentage.
  • Functions — recode the active flag into Active/Inactive, and classify each rental as On Time, Late, or Still Out from rental date + allowed duration.
  • Trigger — every insert into the detailed table upserts the matching summary row, including the late-return rate.
  • Stored procedure — truncate, reload, let the trigger rebuild the scorecard. Designed to run with pgAgent after the store closes.

The classification rule

Return status is not stored on the rental row. The function compares return_date to rental_date + rental_duration. Try it with the same logic the database uses:

Extract (the heart of the pipeline)

The nightly job is this join, plus the two functions, inserted into the detailed table. Payments are summed first so a rental with more than one payment still appears once.

SELECT
    r.rental_id,
    r.rental_date,
    r.return_date,
    i.store_id,
    c.customer_id,
    (c.first_name || ' ' || c.last_name) AS customer_name,
    fn_account_status(c.active) AS customer_status,
    f.film_id,
    f.title AS film_title,
    cat.name AS category_name,
    f.rental_duration AS rental_duration_days,
    COALESCE(pay.payment_amount, 0) AS payment_amount,
    fn_return_status(
        r.rental_date::TIMESTAMP,
        r.return_date::TIMESTAMP,
        f.rental_duration
    ) AS return_status
FROM rental AS r
INNER JOIN inventory AS i     ON r.inventory_id = i.inventory_id
INNER JOIN film AS f          ON i.film_id = f.film_id
INNER JOIN film_category AS fc ON f.film_id = fc.film_id
INNER JOIN category AS cat    ON fc.category_id = cat.category_id
INNER JOIN customer AS c      ON r.customer_id = c.customer_id
LEFT JOIN (
    SELECT rental_id, SUM(amount) AS payment_amount
    FROM payment
    GROUP BY rental_id
) AS pay ON r.rental_id = pay.rental_id;

How a manager is supposed to use it

  • Open the summary. Find categories with high revenue and a high late-return percentage — demand is there, copies are not recirculating.
  • Drill to the detailed table for that store and category. Call Still Out first, then Late. Flag Inactive customers who still have a copy.
  • Decide whether to buy more copies or tighten the hold policy. Do not celebrate a revenue spike that is trapping inventory off the shelf.

Refresh is nightly, after close, so the morning shift has a current call list without querying live rental tables all day.

What I would do next in a production shop

Add store location and days overdue (those fields are not in the lab tables, so they were not invented here). Expose the summary as a small dashboard with a Still Out queue. Track whether call-backs actually recover copies — the report should change behavior, not just describe it.
