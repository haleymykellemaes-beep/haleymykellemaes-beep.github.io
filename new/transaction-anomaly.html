Question

How should a payments team allocate a hard daily review budget?

Approach

Profile, time-split, test each rule, score eligible transactions, then rank the holdout.

Control

Keep labels out of feature logic and exclude post-outcome balance fields from the score.

Decision

Use the scored queue; retire the noisy receiver-velocity rule and monitor drift.

The operating question

Fraud detection is not only a classification problem. It is a queue-management problem. A control with high recall can still fail operationally if it creates more alerts than investigators can clear. I fixed capacity at 200 reviews per day before evaluating the holdout, then compared every approach at that limit.

Data and split

I used the public PaySim synthetic mobile-money dataset: 6,362,620 transactions across 743 hourly steps. It contains 8,213 labeled frauds (0.1291%). Fraud appears only in TRANSFER and CASH_OUT: 4,097 and 4,116 cases, respectively.

Rules and weights were developed on steps 1–480 (days 1–20). Final numbers use only steps 481–720 (days 21–30). I excluded steps 721–743 because they are a partial 31st day. This matters: a filter of step > 480 would quietly contaminate the ten-day denominator.

Distribution shift: training contains 6.04 million transactions at 0.0886% fraud; the holdout contains 322,905 at 0.8027%. That makes this a useful stress test, but not a stable production estimate. A live system would monitor alert volume, precision, recall proxies, and feature drift by day.

Data-governance check: balance fields are leakage

The dataset publisher warns that fraudulent transactions are canceled and that old/new balance fields should not be used for fraud detection. That invalidates “sender drained” and “balances do not reconcile” as deployable signals in this dataset. The drained-account condition appears to catch 97.45% of holdout fraud, but it reads the simulator’s post-outcome state. Reporting that as model performance would be leakage.

  • Point-in-time features only. Candidate controls use transaction type, amount, time, and prior receiver activity; the final portfolio score drops receiver velocity.
  • Labels isolated. is_fraud is used for training selection and evaluation, never in rule expressions.
  • Temporal holdout. Thresholds and weights are frozen before days 21–30 are scored.
  • Exact capacity. Results are measured at 2,000 reviews over ten holdout days.

R1 · Account drained Exclude Uses post-transaction balance state; apparent recall is leakage
R3 · Balance mismatch Exclude Simulator artifact and 11,715.7 holdout alerts/day

Receiver velocity was a reasonable money-mule hypothesis, but the data rejected it. On training, nearly all receiver counts above one were normal. The rule also collapsed from 1,718.8 alerts/day in training to 0.4 in holdout because transaction volume changed sharply. A security analyst should remove a control that does not generalize—not preserve it because the narrative sounds plausible.

Score design

Only TRANSFER and CASH_OUT enter the review queue because those were the only fraud-bearing types in training. The frozen score is:

Risk score = 10 × baseline flag + 1 × large amount + 4 × off-hours + amount z-score
amount z = (amount − training mean for type) / training standard deviation for type

I selected the weights against the 4,000 available training reviews (200 per day for 20 days), with a simplicity tie-breaker. The z-score is not a separate machine-learning model; it is a transparent statistical ranker that makes amounts comparable across transaction types. The rules-only comparison uses the same rule points and FIFO ordering within ties.

Limitations

  • Synthetic behavior: PaySim is appropriate for a reproducible portfolio study, not for estimating loss reduction in a live payments environment.
  • Off-hours artifact risk: transaction volume falls sharply overnight while injected fraud remains comparatively steady. The rule needs shadow-mode validation on real traffic.
  • No customer history: 6,353,307 unique senders appear across 6,362,620 transactions. Sender-history features would be mostly meaningless.
  • Concept drift: the holdout has lower volume and a much higher fraud rate than training. Thresholds should be monitored and recalibrated on rolling windows.
  • Recall is not loss capture: every fraud is counted equally here. A production program would also report dollars prevented, false-positive cost, time to decision, and investigator disposition.

What I would do next

In a live environment, I would run this score in shadow mode, add device, IP, authentication, beneficiary age, and confirmed-loss data, then calibrate the queue by expected loss rather than event count alone. I would monitor population stability, per-rule alert volume, investigator agreement, and recall at fixed capacity. The same control-design pattern extends to security telemetry: impossible travel, failed-login bursts, new-device access, and service-account anomalies using public LANL authentication data.
